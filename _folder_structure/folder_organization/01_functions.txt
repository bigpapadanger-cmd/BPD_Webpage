Continuation: api/admin/rocketleague/custom-match-host-recovery.js uses current
Admin authorization and the fixed admin_transfer_custom_match_host RPC.
The ordinary RL service refuses Admin recovery. Browser input has public
match/member codes, version, idempotency and reason, never actor UUIDs.

ROLE

functions/ contains the Cloudflare Pages server-side layer. Files under api/
provide file-based request routes; files under services/ contain reusable logic,
provider clients, authorization, storage, and database operations. The normal
dependency direction is api/* -> services/* -> Cloudflare bindings/external APIs.

SUBCATEGORY RESPONSIBILITIES

api/auth
    HTTP entrypoints for sessions, account/provider linking, OAuth callbacks,
    provider-specific login/callback flows, Rocket League account data, admin
    authorization, Taskboard APIs, and Discord Matchbot operations.

api/suggestions and api/admin/suggestions
    Publicly list approved suggestions; require an active BPD session for
    submissions and vote toggles; require the server-side
    admin.suggestions.manage permission for pending-list and review actions.

api/ocr
    Synchronous OCR-facing endpoints plus the queued-job lifecycle. jobs/
    submits work, exposes stored image/job/progress/result data, and accepts the
    processor callback used by the queue consumer.

      Queued submissions accept legacy roster fields or the additive
      sourceMode/submissionMode contract. Automatic roster metadata may be absent;
      manual metadata remains strictly validated. Result readers accept current
      and historical team/field shapes. Team totals are exposed only when
      explicitly stored.

services/auth
    Shared request authentication/authorization, session context, account
    mutations, generic OAuth flow, and provider-specific implementations.

services/rl
    Rocket League authorization/profile/session logic, presence-monitor calls,
    and MMR fetch/cache/refresh/save flow.

services/ocr
    Request handling, image/training storage, OCR service calls, localization,
    confirmation, and match persistence support.

services/supabase
    Direct persistence boundary for Rocket League profiles/MMR/player discovery and admin
    Taskboard activity, assignment, comments, lifecycle, list/get/create/update,
    summaries, payloads, and RPCs. rest.js retains the configured /rest/v1 base
    and applies the same-origin, REST-path-bounded redirect policy for the
    Users, Notifications, and Leaderboard RPC/table callers.

services/supabase/suggestions.js
    Calls only the five website-suggestion RPCs defined by the local-only,
    operator-prepared Supabase contract under Notes/supabase/suggestions/.

services/faq/service.js
    Published FAQ projection, authenticated question submission, and BPD User
    Management-authorized review. Uses only list_published_faqs,
    submit_faq_question, admin_list_faq_questions, admin_review_faq_question RPCs.
    Service-role key stays server-side; current post access gates mutations.
    Admin list derives read-only/review UX from existing admin_list_users
    permissions; FAQ RPCs remain final authority. No Discord role authorization.
    Strict origin/body validation, bounded provider responses/deadlines, private
    field stripping, safe domain errors, idempotency and revision forwarding.
    Service credentials remain server-side; public browser clients never
    receive direct Supabase access. The SQL is outside the Pages deployment tree
    and excluded from GitHub by .gitignore.

services/supabase/rocketleague/discovery.js
    Server-only, allow-listed search/public-profile/featured/network-statistics
    RPC transport with an 8-second end-to-end deadline, bounded response bodies,
    and explicit public-field sanitization. Featured reads are not publicly cached.

services/admin, services/security, services/config, response helpers
    Cross-cutting permissions/Discord roles, Turnstile validation, environment
    configuration access, and consistent HTTP response construction.

services/admin/mmr_deployment.js
    Fixed-target GitHub workflow dispatch, five-minute deployment guard,
    sanitized RL_STATS_CACHE state, run polling, and post-deploy MMR health.

api/admin/system-status/mmr-deploy.js
    Dedicated admin.mmr.deploy route. Accepts only explicit confirmation and
    never accepts a repository, branch, workflow, Worker name, or command.

User Management list diagnostics (GET /api/admin/user-management): request-local,
server-generated X-Debug-ID correlates one [USER MANAGEMENT DIAGNOSTIC] completion
record. Optional diagnostic context follows existing session/account authorization
and account-access RPCs, then admin_list_users decode/permissions/normalization.
Only fixed stage/operation/RPC, allowlisted code, numeric upstream status, deadline
state and elapsed time are logged. No request data, identity, credentials or raw
error/payload is serialized. Other routes do not enable this context.
Reproduce after an authorized release: sign in with an existing authorized User
Management account, open /Admin/UserManagement, use Refresh once, capture the GET
response X-Debug-ID in browser Network, and filter Pages server logs for that ID.
Share only the diagnostic record and response status/error; do not export a HAR.
No deployment or Supabase change is performed by this diagnostic implementation.

Published FAQ diagnostics (GET /api/faq): server-generated X-Debug-ID correlates
one [FAQ DIAGNOSTIC] completion record. Stages cover FAQ service/configuration,
list_published_faqs fetch, bounded body read, decode, rejection and normalization.
The existing complete-operation deadline and 2 MiB response cap remain unchanged.
Success and failure remain no-store; browser JSON and curated static FAQ content
are unchanged. Only operation/stage/RPC, allowlisted code, numeric upstream HTTP
status, elapsed time and deadline/timeout state are logged, plus the debug ID.
No credentials, environment values, request data or raw payload/error is logged.
The shared http/diagnostics.js helper preserves the 2A logging/header contract.
2A diagnostics: PASS locally. Production User Management root cause: BLOCKED
pending authorized release and reproduction evidence; no speculative repair.
2B production FAQ root cause likewise remains pending runtime evidence.
Release validation: after a separately authorized release containing diagnostics,
open /FAQ with browser Network tools active (or GET /api/faq directly), capture
that response's X-Debug-ID, HTTP status and sanitized error, and filter Pages
server logs for the matching [FAQ DIAGNOSTIC] record. Share that record only,
not request headers, raw payloads or a HAR. Public GET requires no Admin session.
No deployment, push or Supabase change is part of this workstream.

HTTP shared utilities: diagnostics.js sanitizes operational metadata; responses.js offers opt-in internal-identifier projection. Auth session serializes accountScope using public/scripts/accountScope.js; canonical server identity remains internal.
