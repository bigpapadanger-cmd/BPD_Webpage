WORKERS/: INDEPENDENT CLOUDFLARE WORKERS
Snapshot: 2026-10-04

ROLE

workers/ contains five separately configured Worker deployments. They do not use
the root Pages wrangler.jsonc at deployment time; each child owns its entrypoint,
bindings, routes, triggers, and observability settings.

Discord MatchBot runtime status: bpd-provider-runtime is a stateless, private
REST validator with no Gateway session, guild registry persistence, or schedule.
Pages and the hourly refresh Worker call it through Service Bindings; DomainData
owns canonical identity resolution, Supabase inventory/state RPCs, freshness,
batching, forced rechecks, and safe UI responses. Existing MatchBot REST services
and signed interaction routes also remain under functions/; they are request-
driven and do not receive Gateway READY/GUILD_CREATE/GUILD_DELETE lifecycle
events.

OCR JOB CONSUMER

Configuration
    Worker name       bpd-ocr-job-consumer
    Entry             src/index.js
    Custom domain     ocr.bpd-gaming-network.com (HTTP fetch returns 404; no
                      unauthenticated health response is exposed)
    Queue consumer    bpd-ocr-jobs; batch size 1; concurrency 2; two retries
    Schedule          every 30 minutes for cleanup
    Status            Queue invocation heartbeat in shared status KV; no synthetic HTTP health route.
    R2 bindings       OCR_STORAGE and OCR_PROGRESS
    External callback configured to the Pages process_job API

Runtime relationships
    root Pages wrangler.jsonc produces OCR_JOB_QUEUE messages
        -> src/index.js consumes each message
        -> reads/writes job state and progress in R2
        -> calls the configured OCR processor (ocr_cloudData service)
        -> sends processor results to functions/api/ocr/jobs/process_job.js
        -> acknowledges, retries, or records failure
    scheduled event
        -> cleanup.js removes aged transient progress only; OCR inputs, job
           records, reports, images, and review artifacts are retained
    debug tracing
        -> debug.js writes sanitized diagnostic traces when enabled

ROCKET LEAGUE PRESENCE MONITOR

Configuration
    Worker name       bpd-rl-presence-monitor
    Entry             src/index.js
    Custom domain     status.bpd-gaming-network.com
    KV binding        AUTH_SESSIONS
    Schedules         every 15 minutes for presence, hourly due-aware Rocket
                      League refresh, and a daily Taskboard summary at 12:00 UTC
    External systems  Supabase and the configured MMR API

Runtime relationships
    GET /health
        -> Worker health response
    POST /wake
        -> authorized on-demand presence cycle
    POST /admin/run-scheduled
        -> PRESENCE_TRIGGER_KEY-protected explicit presence/MMR/Shop/Taskboard run;
           returns aggregate-only summary; rejects overlapping same-isolate job
    15-minute cron (unchanged)
        -> presence_cycle.js
        -> API candidate RPC excludes opted-out/ineligible players
        -> authorization recheck and /get-player-data?capabilities=presence
        -> persists only successful normalized online/offline outcomes
        -> provider errors/unknown preserve prior state
    hourly cron
        -> rl_refresh_cycle.js asks api.get_rl_refresh_candidates for up to 20
           due candidates using a cursor in SERVICE_STATUS KV
        -> requests only due MMR/profile/club/career_stats capabilities through
           /get-player-data, persists successful values, and checkpoints each
           component independently
        -> obtains/reconciles one complete bot-guild inventory each hour, even
           when no Discord account is due; only confirmed
           membership sets are synced, then each Discord component is checkpointed
        -> rl_shop_refresh.js calls the protected MMR /get-shop-data endpoint
           once; the MMR Worker makes two PsyNet shop reads
        -> hashes the normalized response and calls api.save_rl_shop_snapshot
           plus api.record_rl_global_refresh_result (key shop)
        -> history remains unsupported for arbitrary scheduled player IDs
    daily cron
        -> taskboard_summary.js
        -> loads Supabase Taskboard aggregates and sends Discord summary output

GOOGLE mTLS DIAGNOSTIC WORKER

Configuration
    Worker name       bpd-google-mtls-diagnostic
    Entry             src/index.js
    Runtime URL       no public route; Pages and rl-presence-monitor use Service Bindings
    mTLS binding      OCR_GCP_MTLS from the configured Cloudflare mTLS certificate
    Triggers          none; no cron, queue, or automatic retries
    Rates             calls occur only for an explicit authorized request:
                      1 STS call for empty/full-sts, 1 STS + 1 IAM call for
                      id-token; health makes no outbound calls
    Secrets           DIAGNOSTIC_BEARER_TOKEN and OCR_GCP_X509_CERT_CHAIN

OCR CLOUD RUN TRANSPORT WORKER

    Worker name       bpd-ocr-cloud-run-proxy
    Entry             workers/ocr-cloud-run-proxy/src/index.js
    Exposure          workers_dev=false, preview_urls=false; custom domain
                      ocr-transport.bpd-gaming-network.com requires
                      OCR_GOOGLE_TRANSPORT_SECRET. Normal caller uses Pages'
                      OCR_GOOGLE_TRANSPORT Service Binding.
    mTLS binding      OCR_GCP_MTLS; same configured Cloudflare client certificate.
    Secrets           OCR_GCP_X509_CERT_CHAIN, OCR_API_KEY, and
                      OCR_GOOGLE_TRANSPORT_SECRET (also set on Pages).
    Request path      Pages process_job or authenticated synchronous OCR handler
                      -> POST internal /api/ocr -> X.509 Google STS -> IAM
                      generateIdToken -> fixed Cloud Run OCR URL.
    Contract          Multipart image only, bounded request/response, fixed
                      upstream. Neither Google token is returned or logged.
    Schedules         none; runs only when Pages OCR submits an upstream request.

TEST OWNERSHIP

The tests stored under rl-presence-monitor/tests cover both Worker behavior and
contracts shared with root application code: account mutations, Epic/OAuth entry
paths, provider authorization, Taskboard service/RPC contracts, and SQL schema
validation. fixtures/taskboard_schema.sql supplies the schema validation fixture.
