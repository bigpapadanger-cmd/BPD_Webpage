OCR_CLOUDDATA/: PYTHON OCR SERVICE AND DATA
Snapshot: 2026-10-04

ROLE

ocr_cloudData/ is a separately deployable Python/Flask OCR processor. It accepts
image-processing requests from the Cloudflare OCR job path, runs the Rocket
League scoreboard pipeline, reports progress, and returns structured results.
It also contains local training samples and generated diagnostic output.

PIPELINE RELATIONSHIP

ocr_servercall.py
    -> initializes the bounded scheduler and template cache
    -> calls ocr.pipeline.read_scoreboard_image
        -> preparation.scoreboard_locator locates/crops the scoreboard
        -> preparation.normalization normalizes the image
        -> layout.headers detects column/header geometry
        -> preparation.anchors and preparation.rows reconstruct player rows
        -> layout.cells creates field cells
        -> readers.player_name reads names and matches supplied rosters
        -> readers.numeric_router runs ONNX first, with legacy readers for uncertainty
        -> readers.team_score preserves header geometry and classifies isolated candidates
        -> rules validates resolved field values
        -> readers.candidate_collection builds bounded crops/evidence for review-only archival
    -> progress_store reports job progress to the configured Cloudflare endpoint
    -> returns structured OCR output to the queue consumer/callback flow

The Cloud Run process never writes to Cloudflare R2 and never inserts OCR
predictions into numeric training classes. The Pages `process_job` route uses
its existing `OCR_TRAINING` R2 binding to archive candidate crops under
`ocr-training-candidates/YYYY/MM/DD/{jobId}/`; the queue consumer only calls
that Pages route and continues to use `OCR_STORAGE` for job data. Candidate
approval is manual and training import is an explicit local command.

ROSTER AND TEAM TOTAL BEHAVIOR

Manual source mode requires a complete, unique roster and retains legacy
validation. Automatic mode probes symmetric visible row evidence from 1v1
through 16v16, leaves names unassigned when evidence is uncertain, and marks
roster/name uncertainty for review. Player-name reading uses Tesseract. Player
SCORE is the only required displayed numeric player statistic; PING is optional.
Only explicitly detected known headers create player-stat cells. Inferred
lattice positions may support row geometry, but remain unnamed and do not map
to GOALS/ASSISTS/SAVES/SHOTS in output. A genuinely detected GOALS header is
read only to corroborate the large team-header total.

The large team-header OCR value is authoritative. A detected player GOALS column
can validate it; disagreement retains the header value and requests review.
Team-header OCR uses a far-left ROI bounded by player-name geometry, not SCORE
or custom-stat columns; local diagnostic step 09 outlines each ROI and digit.

BOUNDARY WITH THE REST OF THE PROJECT

This folder is not imported by the JavaScript application. The integration is
over HTTP: the Pages configuration and OCR queue consumer identify the processor
URL, while OCR progress/results travel through Cloudflare endpoints and R2-backed
job data. Root eng.traineddata supplies Tesseract language data used by OCR.
